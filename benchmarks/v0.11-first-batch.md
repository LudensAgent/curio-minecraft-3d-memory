# v0.11.0 first-batch observation-ingest probe

Date: 2026-11-10. This report records the resident-byte-accounting change on
`dev/v0.11.0`. It is a synthetic core measurement, not a release acceptance
result or evidence of Minecraft gameplay performance.

## Compared sources and environment

| Item | Value |
|---|---|
| Before | Commit `32656b6`, exported with `git archive` and built from source in an isolated temporary directory |
| After | `dev/v0.11.0` working tree with incremental resident accounting, exact batch capacity preflight, and indexed palette lookup |
| Runtime | Node.js `v24.14.1` |
| Platform | Windows x64 (`win32`, `x64`) |
| Probe | [observation-ingest.bench.mjs](./observation-ingest.bench.mjs) |
| Warmup / measurement | Two warmup rounds, then five measured rounds per scenario |
| Updates per round | 256 observations with increasing acquisition times |

Both source trees were built before the reported measurements. The before
temporary directory was removed after measuring. These runs shared the
development machine with other work; CPU isolation, event-loop-delay and GC
measurements were not part of this probe. Millisecond-scale differences and
outliers should not be treated as stable absolute thresholds.

## Workloads and timing boundary

Each scenario pre-fills one resident 16×16×16 Section with 128, 512, 2,048 or
4,096 observed stone cells. Initialization and input construction are excluded
from timing. Each round measures either 256 consecutive `observe()` calls or
one `observeBatch()` call containing the same 256 inputs.

- `same-cell-refresh`: all 256 inputs refresh the same existing stone cell.
  This matches the before probe's workload.
- `multi-cell-refresh`: inputs address `index % cells`, refreshing existing
  stone cells. At density 128, each of the 128 cells appears twice; at larger
  densities, the round touches 256 distinct cells.
- `multi-cell-state-change`: the same coordinates alternate between stone and
  dirt across rounds. At density 128, there are 128 changes followed by 128
  same-state refreshes per round; at larger densities, all 256 inputs change
  state. Both states enter the palette during warmup.

The distinct observed-cell count is checked after each scenario. The duration
of a round is a synchronous interval; dividing it by 256 gives an average cost
per input, not a latency percentile for individual observations.

## Before / after: manual residency

Median duration per 256-input round, in milliseconds:

| Known cells in Section | Before single | After single | Before batch | After batch |
|---:|---:|---:|---:|---:|
| 128 | 7.857 | 0.457 | 0.417 | 0.429 |
| 512 | 30.412 | 0.382 | 0.423 | 0.264 |
| 2048 | 122.041 | 0.394 | 0.806 | 0.248 |
| 4096 | 247.384 | 0.433 | 1.228 | 0.297 |

The old single-observation path estimated all evidence in the Section before
and after each accepted input. Its cost increased with Section density. The
new path updates per-cell and palette byte deltas, so this probe no longer
shows that density-dependent growth. The capacity preflight models repeated
updates to a cell in batch order instead of reserving a new Section-sized
allowance for every input.

The byte ledger follows the existing conservative resident-size estimator; it
does not measure the JavaScript heap. The change removes repeated estimation
work while keeping that accounting contract.

The before numbers above came from this task's isolated rebuild of
`32656b6`; they are separate from the older results quoted in the
[upgrade design](../docs/v0.11.0-upgrade-plan.md).

## Reproduction

From the repository root, build and then run the probe:

```sh
npm run build
node benchmarks/observation-ingest.bench.mjs
```

The recorded after run used the equivalent direct compiler command:

```sh
node node_modules/typescript/bin/tsc -p tsconfig.build.json
node benchmarks/observation-ingest.bench.mjs
```

The script prints runtime metadata, workload names, density, delivery mode,
median, maximum and mean-per-input values as JSON. To reproduce the before
measurement, export commit `32656b6` into a separate directory, make the same
dependencies available, build that source, and run its original
`benchmarks/observation-ingest.bench.mjs`. Do not measure current sources
against an unidentified old `dist` directory.

## Limits and remaining acceptance work

This probe has no database, Worker, cold-page load, observation queue, host
perception loop, route execution or Minecraft server. The reported intervals
are not p95/p99 latency measurements and do not establish the upgrade plan's
control-loop, persistence ACK or sustained-throughput targets.

It holds the world to one Section and reuses a small fixed set of states. It
does not measure unseen palette-state insertion, palette reclamation, a large
cold directory, four million distinct observations, 10,000 repeated journeys,
8-hour input, failure/backpressure, memory growth or game arrival accuracy.
Automatic palette reclamation is not part of this first-batch change.

The extended state-change workload verifies the local update path under real
content changes; its 256 inputs cannot stand in for long-running movement
across many Sections. The remaining M1/M4/M5 workload and release gates in the
upgrade design remain open.
