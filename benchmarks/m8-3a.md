# M8.3 H2 — topology/fragment paging index before/after

This file records **measured data only** for plan §M8.3 H2 (materialized
`listAll`/ordered index + cached `total`). It is **not an acceptance result**
and not a pass/fail gate. The acceptance evidence is the test suite; this is the
before/after comparison the plan requires.

## What changed

`TopologyStore.nodes`/`edges` and `FragmentStore.fragments`/`traversals` used to
`filter + sort` every record on every page, retallying `total` each time. They
now read from a lazily materialized, id-ascending index:

- one ascending id list plus per-field buckets (`dim`, `source`, `tag`, `label`
  for nodes; `dim`, `from`, `to`, `type`, `basis` for edges; `dim`,
  `geometrySource`, `kind` for fragments; `dim`, `fragmentId` for traversals);
- a page is a direct slice of the bucket that exactly expresses the single
  requested condition, so its `total` is the bucket length;
- multi-condition filters scan the first existing bucket by a fixed key priority
  and test the rest, with `total` still counting every match independent of the
  `after` cursor;
- the cursor lookup is now a binary search instead of a linear scan.

The index is a **derived view**, not a second source of truth. Every write that
can change a listing (`saveNode`/`updateNode`/`forgetNode`/eviction,
`saveEdge`/`updateEdge`/`forgetEdge`, `saveFragment`/`updateFragment`/
`forgetFragment`, `addTraversal`, both `restoreSnapshot`s) invalidates it and the
next read rebuilds it from the store maps. Writes never consult the index, and
no read returns an item the store no longer holds.

Visible set, order, `total` and `after`/`nextAfter` semantics are unchanged;
`tests/topology-listing-index.test.ts` compares every combination against the
pre-index linear reference over the fixture arrays used to populate the store
(the `restoreSnapshot` case restores from `checkpointSnapshot()` input and
compares the result against the fixture linear reference).

## Method

From the worktree root:

```bash
npx tsx benchmarks/paging-query.bench.ts
npx tsx benchmarks/fragmentation.bench.ts
```

Each run prints one markdown table; every row is the median of 5 timed rounds
after one discarded warm-up. **Two passes** were recorded for the pre-change and
two for the post-change state on the same machine, in one sitting:

- **before**: `git stash push -- src/topology/topology-store.ts
  src/topology/fragment-store.ts` restored the `7a2dd54` files; both benchmarks
  ran twice; `git stash pop` restored the change. (These are the `baseline.md`
  scenarios with unchanged fixtures.)
- **after**: both benchmarks ran twice on the working tree.

The fixture files and `benchmarks/baseline.md` thresholds were not modified.
`baseline.md` is the published M8.1 snapshot (drain nodes 206.1 ms p95, drain
edges 217.1, drain traversals 195.9, fragmentation 231.9 on that run's machine
state); the local pre-change pass below is the like-for-like reference for this
comparison, because the M8.1 snapshot was taken on a less loaded machine.

| populate 1000 fragments + 20k links (setup) | 17.79 / 18.65 | 17.10 / 17.67 | 18.65 | 17.67 | 75.7 / 91.3 MiB |

Scale: `fragments=1000 traversalLinks=20000 points=9869 components=1250`.
`fragmentation()` drains the dim lists through the paged readers, so the
pre-change per-page sort over all 20 000 traversals was most of its cost; that
cost is gone. The union-find itself is unchanged.

## Conclusion

- Store paging and the query port's joined pages are **order-of-magnitude**
  faster (first page 1.0 → 0.013 ms; drain 20 000 nodes 204 → ~1.7 ms; drain
  20 000 edges 215 → ~15 ms; drain 20 000 traversals 191 → ~1.0 ms).
- `components` and `fragmentation`, which drain the same lists internally, also
  improve (~2× and ~9× respectively); their own algorithms were not changed.
- Setup time, `adjacency` and the visible semantics are unchanged.
- Every improvement is a page-index effect; no contract-visible behavior changed.
  The `total`/cursor/visible-set equivalence is covered by
  `tests/topology-listing-index.test.ts`, including add/update/delete, eviction,
  fragment-delete cascade and `restoreSnapshot`.
- Limitation: a workload that interleaves a write with a read rebuilds the index
  on that read, at the same O(N log N) cost the old listing paid on *every* read.
  The benchmark measures read-heavy paging, which is the audited hot path; no
  interleaved write/read measurement is claimed here.
