# M8.3 H5 — route verification/execution before/after

This file records **measured data only** for plan §M8.3 H5 (`RouteVerifier` /
`WalkRouteExecutor` per-step route work) and audit §11.1 H5. It is **not an
acceptance result** and not a pass/fail gate. The acceptance evidence is the
test suite; this is the before/after comparison the plan requires.

## What changed

`WalkRouteExecutor.advance()` used to take four full `RouteStatus` snapshots per
route step, and each snapshot:

- scanned every verified result for TTL expiry;
- re-polled `map.residencyGeneration()` for every dependency of **every**
  verified step; and
- deep-cloned every verified `StepEvaluation` into the public `steps` array.

`RouteVerifier` also re-sorted the entire pending index set on every round.
No CPU profile was captured for this record; the statement is about the work
the code performs, and the before/after table below is the measured evidence.

The changes keep every public status field and verdict rule, but the per-step
work is now incremental:

- **Pending cursor.** Pending indices are still processed in ascending step
  order, but a `pendingCursor` replaces `[...pending.keys()].sort()` per round.
  Invalidation moves the cursor backwards (`min`), so a re-queued earlier step
  is still re-verified before later pending ones.
- **Section residency index.** The verifier records the residency generation
  once per **distinct dependency section** (`sectionResidency`) instead of once
  per verified step, and checks each distinct section per round. A changed
  generation still invalidates exactly the steps in `sectionToSteps`.
- **Gated expiry scan.** `nextExpiry` holds the earliest non-STALE horizon.
  `expireStale` is a no-op until the clock passes it; an invalidation sets
  `expiryDirty`, which forces a rescan (and recomputes the horizon).
- **Internal step accessor.** `RouteVerifier.stepAt(i)` returns one step's
  evaluation with the same reconcile/expiry/residency freshness as `status()`
  but without cloning the route. `currentRuleVersion()` reads the rule identity,
  and `advanceVerification(budget)` performs the bounded round without building
  a throwaway `RouteStatus`. `WalkRouteExecutor` uses these three on its
  per-step paths; its public `snapshot()` still builds one full `RouteStatus`.
  These methods are marked `@internal` and are **not** added to `src/index.ts`.

Visible semantics are unchanged: step order, ARRIVED/BLOCKED/INVALIDATED/PARTIAL
outcomes, cancel/timeout partial effects, evidence and time fields, and the
immutability of returned snapshots (each `status()` still deep-clones). The
existing focused suites (`route-verifier`, `walk-route-executor`,
`grounded-walk-route`, `known-walk-route`, `land-route`, and the `walk-path-*`
execution suites) pass unchanged; `tests/route-step-accessor.test.ts` adds
discriminators for the cursor reset, per-section residency invalidation, the
expiry gate boundary, rule-version reconciliation through
`currentRuleVersion`/`stepAt`, `advanceVerification` leaving the same state as
`advance`, and `stepAt` agreeing with the `status()` projection.

`src/traversability/land-route.ts` was inspected but **not changed**: it is a
separate `LandRouteVerifier` over typed land transitions, not on the measured
route-execution hot path. No acceptance or benchmark evidence for it was
produced here.

## Method

From the worktree root:

```bash
npx tsx benchmarks/route-execution.bench.ts
npx tsx benchmarks/route-plan.bench.ts
```

`benchmarks/fixtures.ts` runs one discarded warm-up and takes the median of
`RUNS = 5` timed rounds. The script was run **twice before and twice after**,
alternating worktrees on the same machine in one sitting: the before runs in
the clean base worktree `integration-b02` @ `33f4bbb` (no `src/*` changes
applied; benchmarks only read it), the after runs in this task worktree. The
shared machine was not otherwise idle under our control, so run-to-run noise is
reported as-is rather than smoothed.

The benchmark's own disclaimer is repeated here verbatim in substance: the
route-execution fixture uses a **scripted `MoveExecutor` fake that resolves
every single-step move immediately at the requested point**. It is **not a real
Minecraft server and not mineflayer**; it measures the executor + verifier loop,
not network, physics, or world I/O. The fixture map is an in-memory `VoxelMap`
with fake collision rules (`benchShapeProvider`), and every route point is
`(k+0.5, 0, 0.5)` over all-OPEN terrain.

## RouteVerifier + WalkRouteExecutor — before vs after

| scenario | scale | before ms (pass 1 / 2) | after ms (pass 1 / 2) | before worst p95 | after worst p95 |
|---|---|---:|---:|---:|---:|
| populate 1024-point route corridor (setup) | routePoints=1024 | 5.794 / 4.790 | 4.810 / 6.418 | 5.794 | 6.418 |
| execute 1023 steps of a 1024-point route | routePoints=1024 steps=1023 | **1785.445 / 1730.334** | **182.767 / 182.466** | 1789.103 | 184.862 |

Median-of-two improvement: **~9.6×** (1757.9 → 182.6 ms). Worst-p95
improvement: 1789.1 → 184.9 ms (~9.7×). Per-step cost drops from ~1.72 ms to
~0.18 ms at 1023 steps. Setup time is unchanged within noise.

Memory (process peaks reported by the harness, not a controlled measurement):
route-execution RSS peak 213.7–226.3 MiB before, 212.3–229.6 MiB after;
`heapUsed` peak 45.6–79.3 MiB before, 88.1–92.8 MiB after. The after pass does
not claim a memory improvement; the ranges overlap / move in both directions
and the memory sampler is a coarse high-water estimate.

## Conclusion

- Per-step route execution over 1023 steps drops from **~1758 ms to ~183 ms**
  median-of-two (~9.6×); worst observed p95 drops from ~1789 ms to ~185 ms.
- The change is the removal of repeated whole-route work per step: four full
  snapshots → one, one residency check per distinct section instead of per
  step-dependency pair, expiry scans gated by the earliest horizon, and a
  pending cursor instead of a per-round sort.
- Public `advance()` still builds a full `RouteStatus` per call, so a caller
  that invokes `advance()` once per step retains O(n²) snapshot construction
  proportional to its own per-call snapshot reads. The executor no longer does
  that: it builds one status per executor step, not four.
- No contract-visible behavior changed; the semantic equivalence is covered by
  the existing focused suites plus `tests/route-step-accessor.test.ts`.
